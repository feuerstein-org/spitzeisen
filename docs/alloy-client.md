# Alloy client support and Python extensions

Spitzeisen generates JSON clients from `alloy#simpleRestJson`, using Alloy 0.3.40. This replaces
the private `genericRestJson` protocol and the previous partial `restJson1` handler. It reuses an
established specification, trait definitions, and selected upstream tests. Spitzeisen still owns
its Java generator, Pydantic integration, and Python transport. Adopting Alloy does not install a
Python SDK generator or oblige this project to implement every Alloy feature.

Java, Smithy, and Alloy are build dependencies. Deployed SDKs need the Python runtime only.

## Supported subset

The service must declare the protocol explicitly:

```smithy
use alloy#simpleRestJson

@simpleRestJson
service ExampleService {
    version: "1"
    operations: [GetRecord]
}
```

Only included operations are validated; `@spitzeisen.api#excludeOperation` can omit an operation
that will be implemented by hand. Unsupported wire features produce generation errors rather
than silently selecting different encodings.

| Feature | Current behavior |
| --- | --- |
| Generated HTTP methods | GET with a JSON success body. Other methods and 204/205 fail generation. |
| Path labels | Standard and greedy labels, with percent encoding. |
| Query bindings | Scalars, repeated list values, and `httpQueryParams` maps of strings or string lists. Explicit query bindings take precedence over map entries. |
| Query encoding | RFC 3986 percent encoding. URI query literals are rejected; use an explicit query member with a default. |
| Request headers | Scalars and timestamp formatting. Header collections and prefix-header maps are rejected. |
| Generated results | JSON objects or lists of objects, optionally selected from one envelope level. Structure models are generated; object-valued Documents can use an external Pydantic model. |
| JSON members | Ordinary scalar, enum/intEnum, structure, list, map, and Document data; `jsonName` aliases and client presence/default rules. |
| Timestamps | JSON response timestamps use date-time. Request timestamps support date-time, http-date, and epoch-seconds according to their binding. |
| Response headers/status bindings | Rejected by generated methods. Available to handwritten response decoders. |
| Errors | Existing status-based exceptions, preserving raw body and headers. JSON and plain-text messages are retained. No modeled error classes or X-Error-Type dispatch. |
| Advanced encodings | Unions, blobs, streaming, endpoint/host-label transformations, mediaType, and additional Alloy encoding traits are rejected. This includes Alloy nullable, custom date/time formats, and union-discriminator traits. |
| Validation | Pydantic type/structure checks; stronger input and response constraint checks remain opt-in. See the README for client optionality and enum evolution behavior. |

The subset can expand when a supported API needs another feature. Implement its wire behavior,
add applicable upstream cases and generated SDK tests, and update this table together. Changing
the dependency pin alone must not silently enable a new encoding.

## What remains SDK or vendor policy

Alloy defines HTTP/JSON behavior. Authentication configuration, rate-limit costs, retry choices,
pagination workflows, sorting conventions, and Python helper methods remain Spitzeisen or SDK
responsibilities. Existing portable traits for result selection, page numbers, sorting, client
defaults, exclusions, and adapter IDs remain available.

CSV responses, vendor-specific error interpretation, arbitrary nested result extraction, cursor
or next-URL pagination, and WebSocket/streaming workflows are not generated by this subset.
Buffered CSV and other ordinary HTTP responses can use the shared request method below.
Streaming requires a separate transport design. A vendor's nanosecond Unix count should normally
remain an Integer/Long; it is not an Alloy epoch-seconds Timestamp.

## Preserving Python customization

Public operation, client, and model subclasses are created once and preserved by regeneration.
Files under `_generated/` and `_exports.py` are replaced. Put helper methods in public operation
subclasses and custom field validators/properties in public model subclasses.

Use `external_models` in the Python settings file to replace a selected response root with a
handwritten Pydantic model. Substitution inside another generated response model is not supported;
replace the enclosing root when custom nested types are needed. For structurally irregular JSON
objects, model the payload as Document, register its external model, and set the result explicitly,
for example `@spitzeisen.api#result(path: ["payload"], cardinality: "single")` on the operation.
Use `cardinality: "collection"` for a JSON array of such objects. Custom model validation
belongs to that model and is not automatically governed by the generated constraint policy.

Use `@spitzeisen.api#inputAdapter(id: "symbols")` and a matching `input_adapters` entry to accept
a custom Python type while keeping Smithy's shape faithful to the wire. For example, an API
expecting `symbols=AAPL,MSFT` has a String query value. Its Python adapter may accept `list[str]`
and return `",".join(value)`. A Smithy list has repeated-key semantics instead.

For an endpoint with a different response format, add a helper using the public request path:

```python
import csv
from io import StringIO

from httpx2 import Response
from pydantic import BaseModel
from spitzeisen import AsyncSpitzeisenApi, SpitzeisenOperationSpec


class Row(BaseModel):
    symbol: str
    price: float


def decode_csv(response: Response) -> list[Row]:
    return [Row.model_validate(row) for row in csv.DictReader(StringIO(response.text))]


class AsyncRecordsApi(AsyncSpitzeisenApi):
    async def export(self) -> list[Row]:
        return await self.request(
            SpitzeisenOperationSpec(path="/records.csv", cost=2),
            decoder=decode_csv,
        )
```

An SDK can put the same method on an existing public generated operation subclass. The sync
surface uses `SyncSpitzeisenApi` and a regular method without `await`.

This path shares authentication, per-attempt rate limiting, retries, timeout configuration, and
connection ownership with generated JSON methods. The decoder runs on the buffered successful
response; decoder errors propagate without retrying. HTTP failures are raised before decoding.
Pass query values through `serialize_query_param`. For a templated path, supply `path_params`
with values encoded by `serialize_path_param`, choosing greedy encoding only for greedy labels.
Inspect `HTTPError.body` and `HTTPError.headers` for custom error handling; an exhausted 429 retry
preserves that HTTPError as `MaxRetriesExceededError.__cause__`.

Handwritten operations can set `method="POST"` (or another supported HTTP method), supply `content`
as serialized bytes, and set the Content-Type header. POST and PATCH have no automatic retries.
Set `retryable=True` only when replay is safe for that endpoint. Streaming request bodies are
rejected so retry attempts cannot consume an already-read stream.

## Migration and verification

1. Replace the old service protocol declaration with `alloy#simpleRestJson`. Update any
   `protocol_preference` setting, or omit it when the service declares only Alloy.
2. Remove `queryEncoding` traits. Keep repeated values as Smithy lists; model vendor delimited
   values as String with a Python adapter. The legacy trait is retained only to report a useful
   migration error.
3. Review imported OpenAPI models and their overlays. Importing through smithy-translate does
   not establish protocol conformance; explicitly select Alloy only for compatible operations.
   The existing OpenAPI 3.0 ingestion restrictions still apply.
4. Regenerate, run `spitzeisen-gen check`, and exercise representative vendor requests. Keep
   exceptional formats in handwritten helpers or exclude them from generated operations.

`tests/test_codegen_sdk.py` loads cases from the pinned `alloy-protocol-tests` Maven artifact.
It exercises `HealthGet`, `GetEnumInput`, `GetEnumOutput`, `GetIntEnumInput`, and `GetIntEnumOutput`
against both generated Python surfaces. Local cases cover query maps, repeated/escaped values,
timestamps, pagination, errors, and preservation of custom Python models/types/helpers.
This is targeted coverage of the supported subset, not a full protocol conformance claim.

The version pin is shared by Python and Gradle in `toolchain.properties`. Gradle uses Smithy's
BOM to keep the generator and transitive test libraries on the same Smithy version. When upgrading, review
the [Alloy specification](https://github.com/disneystreaming/alloy/blob/main/modules/docs/protocols/SimpleRestJson.md)
and [Smithy HTTP bindings](https://smithy.io/2.0/spec/http-bindings.html), update dependency locks
and verification hashes, run Java and Python integration checks, and regenerate the packaged JAR
and example SDK. No Scala or smithy4s runtime is required.
